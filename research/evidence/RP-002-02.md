## 1. Current Hypothesis

### H0

> 企业 AI 要从“理解企业世界”进入“运行企业世界”，可能需要在 Agent 与现有 IT 系统之间建立独立的 Business Action 抽象；高影响业务状态变化不应直接耦合底层 API、系统和数据库。Action 应表达业务意图、状态迁移、权限、风险、审批、预期效果和审计契约；Action Runtime 负责安全可靠地落实执行。

当前状态：Initial / Exploring

---

## 2. Current Research Gap

### GAP-001｜Existing Architecture Equivalence

> DDD Application Service、Domain Service、CQRS Command、Workflow/BPM 等传统企业架构，是否已经承担了 Business Action 的核心职责？如果是，Agent 时代真正新增或显著强化的机制是什么？

本轮重点不是证明“Business Action Layer 存在”，而是判断：

1. 哪些机制早已存在；
2. 哪些只是重新命名；
3. 哪些能力因 Agent 成为新调用主体而发生结构性变化；
4. 是否真的需要独立 Action Layer；
5. 什么情况下直接 Tool / API 更合理。

## 6. Counter Evidence Queue

第一轮主动寻找：

- 传统 Application Service 已经完整承担 Business Action 职责的证据；
- 强 Domain API + Tool Schema 已足够，不需要独立 Action Layer 的案例；
- Workflow / BPM 已经覆盖权限、审批、事务、补偿、审计的实现；
- 微服务成熟企业中新增 Action Layer 反而造成重复抽象的案例；
- 低风险、低复用、单系统场景中直接 Tool / API 更优的反例。
