## 1. 当前假设

### H0

> 企业 AI 要从“理解企业世界”进入“运行企业世界”，可能需要在 Agent 与现有 IT 系统之间建立独立的 Business Action 抽象；高影响业务状态变化不应直接耦合底层 API、系统和数据库。Action 应表达业务意图、状态迁移、权限、风险、审批、预期效果和审计契约；Action Runtime 负责安全可靠地落实执行。

当前状态：Initial / Exploring

## 2. 当前研究 Gap

### GAP-003｜ServiceNow / Salesforce / SAP 的受治理业务状态修改

> ServiceNow、Salesforce、SAP 等企业平台如何让 Agent 执行受治理的业务状态修改？这些产品是否重复出现稳定动作契约、权限/审批、事务/补偿、审计和 runtime binding？

本轮重点不是证明 Palantir 的实现“更先进”，而是判断：

1. Ontology-native Action 是否提供传统 Service / Command / Workflow 不具备的稳定机制；
2. Action 与 Object / State / Permission / Effect 的绑定方式是否形成新的工程能力；
3. 这些机制是否只是既有应用能力在统一语义层中的资产化；
4. 是否存在不需要 Ontology-native Action 也能达到同等效果的反例。

## 4. Evidence Detail

### E-001｜Traditional DDD services already carry business-operation semantics

Source:
- Martin Fowler, “Service Layer”
- Eric Evans / Domain Language, “Domain-Driven Design Reference”
- Microsoft, “Designing a DDD-oriented microservice”
URL:
- https://martinfowler.com/eaaCatalog/serviceLayer.html
- https://www.domainlanguage.com/wp-content/uploads/2016/05/DDD_Reference_2015-03.pdf
- https://learn.microsoft.com/en-us/dotnet/architecture/microservices/microservice-ddd-cqrs-patterns/ddd-oriented-microservice
Date: 2003-03-05 (Fowler); 2015-03 (DDD Reference PDF); 2022-04-13 (Microsoft page; accessed 2026-09-18)
Evidence Type: Architecture Pattern / Theory

Observed Fact:

Fowler defines Service Layer as the application's boundary and set of available operations, encapsulating business logic while controlling transactions and coordinating responses. The DDD Reference defines a Domain Service for a significant domain process or transformation that is not a natural responsibility of an Entity or Value Object, with a named service contract stated in the bounded context's ubiquitous language. Microsoft describes the Application Layer as defining the jobs software must do, staying thin, coordinating tasks, and delegating business rules to the domain model.

Mechanism:

Traditional DDD already separates business-operation intent and domain rules from presentation, persistence and transport adapters. It therefore covers a large part of the proposed Business Action Contract; the semantic mutation boundary is not new merely because an Agent invokes it.

Target Hypothesis:
H-RP002-06

Effect:
Narrows

Confidence:
High

Why it matters:

An independent Action Layer cannot claim novelty from naming a business operation or hiding a database/API call. The remaining question is whether Agent-facing governance and cross-system execution justify a separate reusable asset.

Boundary / Limitation:

These sources describe application/domain boundaries, not model-controlled discovery, multi-agent authority, or a registry spanning bounded contexts.

Research implication:

Treat Action as a possible cross-channel contract or composition over existing services, not as an automatic replacement for Application/Domain Service.

### E-002｜CQRS Command already expresses intent-bearing mutation

Source:
- Martin Fowler, “CQRS”
- Microsoft Azure Architecture Center, “CQRS Pattern”
URL:
- https://martinfowler.com/bliki/CQRS.html
- https://learn.microsoft.com/en-us/azure/architecture/patterns/cqrs
Date: 2011-07-14 (Fowler); 2025-02-22 (Microsoft page; accessed 2026-09-18)
Evidence Type: Architecture Pattern / Implementation Guidance

Observed Fact:

Microsoft states that commands should represent specific business tasks (for example, “Book hotel room”) rather than low-level updates (for example, setting a status field). Its example command handler accepts commands and invokes domain-interface methods. Fowler describes CQRS as separating command/update and query models, while warning that the pattern is suitable only for some complex domains.

Mechanism:

The command boundary already carries business intent, input validation and domain invocation. CQRS can provide the write-side contract that an Agent calls, but its core contribution is read/write separation, not an Agent-specific Action abstraction.

Target Hypothesis:
H-RP002-06

Effect:
Narrows

Confidence:
High

Why it matters:

The proposed Action should be compared against an existing command handler and its authorization/transaction boundary. A new layer must add durable cross-system governance or caller-independent reuse, not only rename commands.

Boundary / Limitation:

CQRS does not by itself define model-facing tool discovery, human confirmation, or durable execution across external systems.

Research implication:

Use Command/Handler as the baseline implementation in any Action-vs-existing-architecture comparison.

### E-003｜Workflow standards and durable runtimes already cover orchestration

Source:
- OMG, “Business Process Model and Notation Specification Version 2.0.2”
- Microsoft Learn, “Durable Functions overview”
URL:
- https://www.omg.org/spec/BPMN/2.0.2/
- https://learn.microsoft.com/en-us/azure/durable-task/durable-functions/durable-functions-overview
Date: 2014-01 (BPMN 2.0.2 publication); 2026-06-03 (Microsoft page; accessed 2026-09-18)
Evidence Type: Standard / Implementation

Observed Fact:

OMG describes BPMN as stakeholder-facing process notation that is precise enough to translate into software process components and independent of a particular implementation environment. Microsoft states that Durable Functions builds stateful workflows and that its runtime manages state, checkpoints, retries and recovery for long-running workflows.

Mechanism:

Process semantics and durable execution are established enterprise capabilities. They already overlap with Action Runtime responsibilities such as orchestration, persistence of progress, retry and recovery; an Agent does not make those primitives new.

Target Hypothesis:
H-RP002-06

Effect:
Narrows

Confidence:
High

Why it matters:

The differentiator cannot simply be “an action can run a workflow reliably.” The research must isolate Agent-specific policy, authority and binding problems that existing workflow runtimes do not solve by themselves.

Boundary / Limitation:

BPMN and Durable Functions do not establish the business meaning of an Agent-selected action or the consent model for a model-controlled caller.

Research implication:

Model Action Runtime as an adapter/composition over workflow and durable-execution infrastructure unless later evidence shows a distinct runtime contract.

### E-004｜Agent invocation adds model-facing governance and safety requirements

Source:
- Model Context Protocol, “Tools” specification v2026-07-28 (latest)
URL:
- https://modelcontextprotocol.io/specification/2026-07-28/server/tools
Date: 2026-07-28 (specification version; accessed 2026-09-18)
Evidence Type: Protocol / Security Boundary

Observed Fact:

MCP tools are designed to be discovered and invoked by language models through `tools/list` and `tools/call`, with input and optional output schemas. The latest specification allows the visible tool set to vary by authorization scope, uses explicit state handles for stateful tools with authorization checked on every call, and supports input-required multi-round trips. It recommends human confirmation for sensitive operations and requires/requests input validation, access control, rate limiting, output sanitization, timeout handling and tool-usage logging; tool annotations must be treated as untrusted unless from trusted servers.

Mechanism:

The new caller is model-controlled and may select tools dynamically or carry state handles across calls, so the system needs stronger model-facing governance requirements around existing business operations: authorization-scoped discovery, schema validation, consent/authority, state-handle validation, untrusted metadata handling and audit. MCP exposes and constrains invocation, but does not define the business state transition or domain rule. Current evidence does not by itself prove that these requirements must become an independent control plane.

Target Hypothesis:
H-RP002-06

Effect:
Supports

Confidence:
High

Why it matters:

This is the strongest Agent-era delta found in GAP-001. It supports a governed boundary around high-impact mutations, but the boundary may be implemented by an MCP adapter plus existing Command/Workflow services rather than a wholly new domain layer.

Boundary / Limitation:

The protocol leaves business authorization semantics, transaction/compensation and domain invariants to the server/application.

Research implication:

Refine “Action Layer” toward a conditional governed mutation contract plus model-facing governance requirements, and test whether those requirements need any separately deployed layer.

### E-005｜Counter evidence: direct APIs remain valid for simple, low-risk work

Source:
- Microsoft, “Designing a DDD-oriented microservice”
- Microsoft, “CQRS Pattern”
- Martin Fowler, “CQRS”
URL:
- https://learn.microsoft.com/en-us/dotnet/architecture/microservices/microservice-ddd-cqrs-patterns/ddd-oriented-microservice
- https://learn.microsoft.com/en-us/azure/architecture/patterns/cqrs
- https://martinfowler.com/bliki/CQRS.html
Date: 2022-04-13 (Microsoft DDD page); 2025-02-22 (Microsoft CQRS page); 2011-07-14 (Fowler; accessed 2026-09-18)
Evidence Type: Counter Evidence / Boundary Condition

Observed Fact:

Microsoft says simpler responsibilities such as CRUD can use simpler approaches and marks CQRS as unsuitable when simple CRUD-style UI and data access are sufficient. Fowler warns that CQRS adds significant mental and implementation complexity and should be used only where its benefits justify the risk.

Mechanism:

For a low-risk, single-system mutation with stable authorization and no long-running orchestration, a strong domain API or command endpoint exposed through a typed Tool Schema can provide an economical path. An extra Action registry/runtime may duplicate service and workflow abstractions without improving outcomes.

Target Hypothesis:
H-RP002-06

Effect:
Opens Alternative

Confidence:
High

Why it matters:

H0 must not become a universal mandate. The burden of proof is higher for an independent Action Layer when the mutation is local, reversible and low impact.

Boundary / Limitation:

This counter-evidence does not cover cross-system, high-impact, approval-heavy or long-running actions where caller governance and audit may dominate.

Research implication:

Carry a direct Tool/API baseline into the next validation and compare it with a governed Action composition under explicit risk and coordination conditions.

### E-006｜Ontology Action is a concrete mutation contract, not merely an API alias

Source:
- Palantir, “Action types • Overview”
URL:
- https://www.palantir.com/docs/foundry/action-types/overview/
Date: 2026-09-18 (accessed; page has no publication date)
Evidence Type: Product Fact / Official Docs

Observed Fact:

Palantir defines an action as a single transaction that changes properties of one or more Ontology objects using user-defined logic. An action type defines a set of object, property, and link edits together with side-effect behavior. The documentation states that the same action logic and validations can be made available across user-facing applications, with changes committed to the Ontology and reflected in applications and the writeback dataset.

Mechanism:

The action boundary is anchored to Ontology object types and the resulting data state, rather than to a transport endpoint or a database field update. It provides a shared, caller-independent mutation definition across Palantir applications. This is a real operational/semantic mechanism beyond exposing an arbitrary API, but it remains a platform-level action configuration over an existing object store and does not by itself prove an independently deployed Action Runtime.

Target Hypothesis:
H-RP002-06

Effect:
Supports

Confidence:
High

Why it matters:

This is the clearest product evidence that placing an action in the Ontology can create a stable mutation contract: object targets, edits, validation, and side effects are packaged once and reused across callers.

Boundary / Limitation:

The page does not establish that this contract is independent of existing application services, nor that it provides atomicity across external systems.

Research implication:

Compare Ontology-native actions with a command/application-service contract on the dimensions of shared semantics, caller reuse, and state binding—not on the mere existence of a named business operation.

### E-007｜Submission criteria and authorizations bind action semantics to state and authority

Source:
- Palantir, “Submission criteria”
- Palantir, “Permissions”
- Palantir, “Read and write authorizations”
URL:
- https://www.palantir.com/docs/foundry/action-types/submission-criteria/
- https://www.palantir.com/docs/foundry/action-types/permissions/
- https://www.palantir.com/docs/foundry/action-types/read-write-authorizations/
Date: 2026-09-18 (accessed; pages have no publication dates)
Evidence Type: Product Fact / Official Docs

Observed Fact:

Submission criteria combine current-user attributes, parameters, object and relation values, and execution context to determine whether an action may be submitted. The permissions documentation separates visibility/edit permissions from the ability to apply a given action and requires the user to satisfy object, datasource, and submission-criteria checks. Read and write authorizations add upper and lower security bounds for data read and data created or modified, while explicitly supplementing rather than replacing ordinary permissions and criteria.

Mechanism:

The action contract can bind business preconditions and authority to the same object/state context that the mutation changes. This is more specific than a generic tool schema: the platform evaluates who may invoke the mutation, against which object state, and what data-security boundary the result must satisfy. It is an Ontology-native governance boundary, but not evidence that every implementation needs a new control-plane service.

Target Hypothesis:
H-RP002-06

Effect:
Supports

Confidence:
High

Why it matters:

It explains why Action is placed beside Ontology objects and state: preconditions, authority, and output-security requirements can be evaluated as part of the mutation definition rather than scattered across clients.

Boundary / Limitation:

Read/write authorizations are documented as beta and the platform still relies on existing permissions. The mechanism is product-specific and does not establish superiority over a domain policy/application-service composition.

Research implication:

Use state-aware authorization and submission criteria as the main comparison dimension against a traditional Command plus Policy Enforcement Point.

### E-008｜Functions are an execution binding under the Action contract

Source:
- Palantir, “Function-backed actions”
- Palantir, “Functions on objects (FOO)”
- Palantir, “Ontology edits”
URL:
- https://www.palantir.com/docs/foundry/action-types/function-actions-overview/
- https://www.palantir.com/docs/foundry/functions/functions-on-objects/
- https://www.palantir.com/docs/foundry/functions/edits-overview/
Date: 2026-09-18 (accessed; pages have no publication dates)
Evidence Type: Product Fact / Implementation Guidance

Observed Fact:

Palantir documents simple rules for common create/modify/delete object and link edits, and function-backed actions for complex multi-object logic. Functions run server-side in an isolated environment with native Ontology object/link access and can return Ontology edits. Those edits do not update live objects merely by running a function; they are applied when the function is configured as an action. Edit provenance is required for action authorization and logging.

Mechanism:

The product separates the stable action invocation/configuration boundary from the code that computes a complex edit. Functions therefore resemble an implementation binding or domain/application service behind an action contract, not proof of a separate Agent-specific runtime. The separation is useful because the same action governance can wrap either declarative rules or code.

Target Hypothesis:
H-RP002-06

Effect:
Narrows

Confidence:
High

Why it matters:

This directly answers the “Action versus Function” part of the gap: Action expresses the permitted mutation and its controls; Function supplies computation and object-edit logic when rules are insufficient.

Boundary / Limitation:

The documentation does not show independent registry semantics, cross-application lifecycle management, or durable coordination beyond the action execution limits.

Research implication:

In architecture comparisons, treat Function as a candidate binding comparable to a Domain/Application Service or workflow step, and test whether the Action contract adds measurable reuse or governance.

### E-009｜Action logs and metrics make the mutation auditable and observable

Source:
- Palantir, “Action log”
- Palantir, “Action metrics”
URL:
- https://www.palantir.com/docs/foundry/action-types/action-log/
- https://www.palantir.com/docs/foundry/action-types/action-metrics/
Date: 2026-09-18 (accessed; pages have no publication dates)
Evidence Type: Product Fact / Observability

Observed Fact:

An action log maps one-to-one with an action type and creates one Ontology log object for each successful submission. Required provenance includes action and action-type identifiers, action-type version, timestamp, current user, edited objects, and webhook/notification/revert provenance. Action metrics separately expose success/failure counts and P95 duration. The log is explicitly not a complete history of every edit path; direct datasource writes and other non-action paths do not produce action log objects.

Mechanism:

The action is treated as an auditable decision/mutation event with versioned identity and context, while observability is kept distinct from edit history. This strengthens the case for a reusable operational contract for high-impact mutations, but also shows that the capability depends on choosing the action path and configuring the log.

Target Hypothesis:
H-RP002-06

Effect:
Supports

Confidence:
High

Why it matters:

Versioned action identity, actor, affected objects, side effects, and performance metrics are concrete mechanisms that an Agent-facing mutation boundary can expose consistently across callers.

Boundary / Limitation:

Coverage is path-dependent and success-oriented; it is not a universal audit layer for all writes, and it does not by itself provide compensation or cross-system atomicity.

Research implication:

Treat audit and observability as part of the value proposition to test, while comparing against existing command/audit/event infrastructure rather than assuming Ontology actions uniquely provide it.

### E-010｜External side effects are not transactionally reverted

Source:
- Palantir, “Side effects”
- Palantir, “Revert or undo actions”
URL:
- https://www.palantir.com/docs/foundry/action-types/side-effects-overview/
- https://www.palantir.com/docs/foundry/action-types/action-reverts/
Date: 2026-09-18 (accessed; pages have no publication dates)
Evidence Type: Counter Evidence / Boundary Condition

Observed Fact:

Action side effects can send notifications or webhooks to external systems, including REST APIs and ERP systems, before or after Ontology edits. When an action is reverted, Palantir states that only the object edits are reverted; notifications and webhooks are not reverted or called again. Reverts are also limited to supported object storage and the user who applied the action.

Mechanism:

Ontology Actions provide a governed mutation boundary and integration hooks, but they do not constitute a general distributed transaction or compensation runtime for external effects. The platform's own documentation therefore sets a boundary on the “Action Runtime” interpretation.

Target Hypothesis:
H-RP002-06

Effect:
Challenges

Confidence:
High

Why it matters:

This is a direct counter to treating Ontology-native Action as a complete replacement for workflow/durable execution. Cross-system reliability still requires explicit workflow, idempotency, compensation, or external orchestration.

Boundary / Limitation:

The evidence concerns Palantir's documented action/revert behavior; it does not rule out other Palantir workflow products or customer-built compensating processes.

Research implication:

Keep “governed mutation contract” and “durable cross-system runtime” as separate claims in H1; the former is supported, the latter remains an engineering gap.

### E-012｜Salesforce Agentforce Action 将状态变更委托给 Flow、Apex 与 API

观察事实：

三个平台文档所呈现的实现模式，都是在既有应用服务、Flow、API 和审批 runtime 之上增加面向 Agent 的 action 或 skill schema。这些来源都没有建立通用独立 Action Runtime、可移植 Action Registry 或跨系统原子补偿层。

机制：

跨平台稳定的最小共同机制，是面向模型的发现加上类型化、经过权限检查的调用。确定性状态迁移、事务、重试、补偿和审计仍是 Flow、Apex、S/4HANA、BPA 或相邻服务的平台特定能力。

Effect：Challenges
Confidence：High

重要性：

边界 / 限制：

本比较基于公开产品文档，而不是受控的实现基准测试。对于高影响跨平台流程或多调用者复用场景，专门的层仍可能产生可测价值。

## 5. 假设演进

### H0

企业 AI 可能需要独立 Business Action 抽象与 Action Runtime，以避免 Agent 直接耦合底层企业 IT。

### H1｜有条件的 Action Contract / 面向模型的治理边界

第一轮 GAP-001 证据修正了 H0。DDD Application/Domain Service 与 CQRS Command 已经承载大部分业务操作语义，BPMN 与持久化 workflow runtime 已经承载流程编排和可靠性。目前证据支持的 Agent 时代增量，是一组面向模型的治理要求：动态发现、类型化 schema、同意/权限、不可信工具元数据处理、输入输出校验、限流和可审计调用。

因此，独立 Business Action Layer 是有条件的，而不是普遍必需的。当前证据尚未建立一个独立的“Agent Control Plane”作为必需架构层。当它能够在多个 Agent/渠道与不断变化的 Service/Workflow 绑定之间提供稳定、与调用者无关的契约时，尤其是在高影响、跨系统、审批密集或长时运行的状态变更中，专门的 Action Registry、治理边界或 Runtime 才可能合理。对于简单、低风险、单系统的 CRUD 类操作，强 Domain API 或通过 Tool Schema 暴露的 Command 仍是可行替代方案。

状态：由 H0 修正而来；未被否定。

### H0 → H1 变化记录

- 旧假设：Agent 到 IT 的执行可能需要独立的 Business Action 抽象与 Action Runtime。
- 触发证据：E-001、E-002、E-003、E-004 和 E-005。
- 变化：传统语义与 runtime 职责已经被大部分覆盖；Agent 特有的治理与模型控制调用是主要增量。
- 新边界：只有当跨渠道稳定性、高影响、跨系统协调或治理需求超出现有 Service/Command/Workflow 组合时，才考虑增加独立层。
- 未解决 Gap：哪些具体风险/协调阈值会让独立 Action Registry 或 Runtime 相比直接 Tool/API 组合产生可测优势。

## 7. 当前判断

GAP-003 本轮获得了 ServiceNow、Salesforce、SAP 官方产品与开发文档的对照证据。H-RP002-06 当前为：

`Revised / Exploring`

GAP-003 当前状态为：

`provisionally_saturated`

原因：三家平台都重复出现面向 Agent 的 action/skill schema、权限检查与既有 Flow/API/Workflow runtime 绑定；但事务、补偿和审计仍由各自平台承担，没有证据证明存在跨平台通用的独立 Action Runtime。概念层边界已清楚，工程收益阈值仍未知。

本轮新增的判断收窄为：

> H1 → H1.1 的本轮跨平台检验：ServiceNow、Salesforce、SAP 均把 Agent 可见的动作/技能契约放在既有 Service、Flow、API、审批与 Workflow runtime 之上。重复出现的是面向模型的受治理状态变更边界，而不是独立、可移植且提供跨系统原子补偿的 Action Runtime。

建议的 proposed revision（仅供 Weekly Synthesis / 人工审核）：

> H1 → H1.1：Business Action 的新增稳定机制可以具体化为与企业对象/状态模型绑定的受治理状态变更契约；Action 与 Function/Workflow 是契约和执行绑定的分离。该机制在高影响、需要统一提交条件/权限/审计、或需要跨应用复用的场景中具有解释力，但跨系统副作用的可靠执行与补偿仍属于 Workflow/Runtime 问题。
