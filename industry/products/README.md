# Products & Company Philosophy｜产品与公司哲学

本目录研究**产业界如何理解企业 AI 问题，以及这些判断如何被工程化成产品机制**。

这里不是传统竞品功能清单，而是把产品视为一种“可运行的组织假设”，再用公开案例、第三方分析、政策标准与反例去验证其边界。

## 产品不是路线

公司、产品、框架和技术热词只是 **Observation Targets｜观察样本**。

真正的产业研究路线见 [`../ROADMAP.md`](../ROADMAP.md)：

- E1 Agent Production / Harness / Runtime
- E2 Enterprise Context / World Model / Ontology
- E3 Capability / Action Infrastructure
- E4 Feedback / Evaluation / Evolution
- G1 Identity / Ownership
- G2 Authority / Policy
- G3 Human Control / Accountability
- G4 Trace / Audit / Lifecycle

研究任何产品时，先判断它主要落在哪些 E/G Track，再映射回 Q1–Q5。

## 一个产品研究卡建议回答

1. **Problem Definition**：这家公司认为企业 AI 的核心问题是什么？
2. **Track Mapping**：主要对应 E1-E4 / G1-G4 哪些产业问题？
3. **Q1–Q5 Mapping**：主要回应决策权、责任、协调、企业边界还是组织学习？
4. **Product Mechanism**：它把哪些能力做成了稳定产品机制？
5. **Product Philosophy**：它反复强调哪些原则、概念或设计语言？
6. **Organizational Assumption**：这些机制隐含怎样的 Human–AI / Agent–Software / Agent–Enterprise 关系？
7. **Evidence Identity**：哪些是 Product Fact，哪些是 Product Claim？
8. **Industry Cases**：有没有公开企业案例支撑？来源来自厂商、客户还是独立第三方？
9. **Analyst View**：是否存在咨询、投研或行业研究机构的独立分析？
10. **Policy / Standard**：如果涉及治理、数据、权限、安全或责任，有哪些公开制度约束？
11. **Counter Evidence**：有哪些失败案例、替代机制、反向观点或不适用场景？
12. **Challenge to Us**：它支持、挑战还是修改本项目已有 JUDGMENTS？
13. **Engineering / Governance Implication**：如果这个产品假设成立，对企业智能工程或治理意味着什么？

## 证据身份必须严格区分

- `[Product Fact]`：公开文档能够确认的具体机制、架构、功能或运行方式；
- `[Product Claim]`：公司对价值、优势、未来趋势或组织含义的主张；
- `[Industry Case]`：公开可核验的企业实践事实或结果；
- `[Analyst View]`：第三方机构的横向产业分析；
- `[Policy / Standard]`：公开政策、法律、监管与标准约束；
- `[Counter Evidence]`：失败、反例、替代路线与边界条件；
- `[Our Interpretation]`：本项目对产品背后组织假设的解释。

必须持续记住：

> **厂商把某机制做成产品，不等于该机制已经被产业或理论证明为普遍正确。**

## 对象选择规则

不提前维护“重点厂商大全”。只有当某个公开产品能够帮助回答当前 Active Research Question，或者能够压力测试 E/G Roadmap 中某条路线时，才建立正式研究卡。

在真正建卡时再核验产品官网、客户公开资料、第三方分析、政策标准和反例，不把未经核验的厂商名单或二手模型结论直接当成事实沉淀。
