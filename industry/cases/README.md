# Industry Cases｜产业案例

本目录只保存**基于公开来源、可公开讨论、能够被外部读者复核的企业 AI / Human-AI 组织实践案例**。

目标不是收集“某公司用了什么模型”，而是回答：现实企业中，AI 进入以后，组织关系和运行机制到底发生了什么变化？

## 进入本目录的最低门槛

一个案例至少应具备可核验的公开来源，并最好出现以下一种或多种结构变化：

- Human / AI 任务重新分工；
- Decision Rights 变化；
- Agent 从建议进入执行；
- Agent 跨多个软件或业务能力行动；
- 多 Agent 协调；
- Human 监督、审批、否决或例外处理机制变化；
- Accountability / Authority 发生重新配置；
- Context / World Model / Semantic Layer 进入运行机制；
- Agent 经验进入企业长期知识、Skill、Rule、Eval 或 Policy；
- 企业内部能力与外部能力边界发生变化。

如果公开案例只有“用了 AI、效率提升 X%”，但没有足够组织过程信息，可以记录结果事实，但不虚构 Human-AI 分工或治理机制。

## 案例研究建议问题

1. **Organization / Context**：公开资料提供了什么组织与业务背景？
2. **Scenario**：AI 进入哪个具体任务或业务链？
3. **Before / After**：公开证据是否足够描述 AI 进入前后的工作结构？
4. **AI Role**：AI 是信息助手、建议者、决策参与者、执行者，还是持续运行主体？
5. **Human Role**：人的角色、决策权、审核权、例外处理和责任是否变化？
6. **Coordination**：Human、Agent、Software、Data、Asset 如何协调？
7. **Engineering Track**：主要对应 E1-E4 哪些产业工程问题？
8. **Governance Track**：主要对应 G1-G4 哪些治理问题？
9. **Q1–Q5 Mapping**：案例主要回应哪些长期组织问题？
10. **Outcome**：公开资料报告了什么结果？口径是什么？
11. **Evidence Quality**：来源是厂商官方、客户官方、独立媒体、Analyst、论文还是其他公开来源？
12. **Boundary / Counter Evidence**：有哪些前提、失败、限制、替代机制或尚未验证部分？

## 证据纪律

- 厂商官网客户案例应标记为 **vendor-reported case**，不能自动视为独立验证；
- 客户自身公开披露通常比厂商转述更接近一手公开来源，但仍需区分事实与解释；
- 宣传指标要保留原始口径和来源，不自行补齐缺失的因果关系；
- Analyst View 可以帮助横向比较，但不等于 Academic Theory；
- 单一成功案例不代表机制可普遍复制；
- 必须主动寻找失败、反例、替代方案与边界条件；
- 本目录只允许公开证据，不保存、引用或描述任何非公开项目材料。

## 推荐文件名

`CASE-<organization-or-topic>-<mechanism>.md`

具体案例只在真正进入当前 Active Research Question 时建立，不为扩目录而批量收集。
